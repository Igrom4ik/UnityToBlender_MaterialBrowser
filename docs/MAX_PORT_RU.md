# Перенос в 3ds Max — план

Цель: второй фронтенд к тому же ядру. Из материалов Unity собирается библиотека
материалов 3ds Max, пригодная к назначению на объекты, — тем же конвейером,
которым сейчас собирается библиотека Blender.

Целевые версии: **3ds Max 2024–2027**, материал — **Physical Material**.
Раскладка: **один репозиторий, два фронтенда**. Проверено на **2027.2**
(Python 3.13.9): установщик, построение материала, запись `.mat`.

---

## 1. Что переносится без изменений

Замерено на текущем коде, а не предположено:

| | |
| --- | --- |
| Ядро `unity_pipeline_core/` | 12 файлов, 102 КБ, `bpy` не импортируется ни разу |
| Совместимость с Python | AST-скан не нашёл ни одной конструкции новее **3.7**: ни `match`, ни рантайм-`\|`, ни `dict[...]` вне аннотаций |
| Blender-надстройка | 9 файлов, 123 КБ — это и есть объём работы, который надо написать заново |

Python в Max 2024–2026 — 3.9 и новее, значит **фаза A переносится копированием**:
парсер `.mat`/`.meta`, GUID-индекс, парсер шейдеров, слой `effective`, side-car
JSON, индекс, отчёт, профили, диффер. `ConversionPlan` уже renderer-agnostic —
он и есть контракт между ядром и фронтендом.

Пять инвариантов действуют без изменений.

## 2. Пайплайн: что выбрано и почему

**Фаза A — вне Max вообще.** Извлечение не требует ни Blender, ни Max: это
чистый Python. Значит `Извлечь` можно запускать откуда угодно, а Max нужен
только для фазы B. В Blender-версии это уже так, но там фазу A всё равно гоняли
внутри сессии; для Max это становится преимуществом, потому что запуск Max
дороже.

**Фаза B — headless через `3dsmaxbatch`.** `3dsmaxbatch.exe <script.py>`
выполняет Python-скрипт без интерфейса — это штатный механизм пакетной
обработки. Сборка библиотеки не занимает рабочую сессию художника и не зависит
от того, что открыто в сцене. Blender-версия от фонового процесса отказалась
(18.1: одна движущаяся часть вместо трёх), но там альтернативой был модальный
оператор в той же сессии; в Max пакетный запуск — документированный штатный
режим, а не самодельный протокол.

**Результат сборки — `.mat`-библиотеки, по одной на каталог Unity.** API
подтверждён: `materialLibrary {}` создаёт временную библиотеку, `append <lib>
<mat>` добавляет материал, `saveTempMaterialLibrary <lib> <файл>` пишет `.mat`
и возвращает признак успеха (доступно с Max 9). Художник открывает `.mat` в
Material/Map Browser и работает штатно, **без плагина** — это главный довод в
пользу такого выхода: библиотека переживает плагин и переносится между машинами.

**Превью отдельным шагом, скорее всего, не нужны.** Blender-версии пришлось
рендерить иконки самой, потому что Asset Browser читает запечённые картинки.
Material/Map Browser рисует сэмплы сам — подтверждаем на M1 и, если так,
выкидываем из плана целый модуль (`preview.py` — 6.7 КБ в Blender-версии).

**Что осознанно не выбрано:**

| Вариант | Почему нет |
| --- | --- |
| Свой PySide-браузер, материалы строятся по клику из JSON | быстро и всегда актуально, но библиотека существует только пока стоит плагин, а drag & drop в вьюпорт из своего Qt-виджета — отдельная война |
| `.max`-файл на материал + Asset Tracking | тысячи файлов и требование открытой сцены, при том что `.mat` даёт то же самое одним файлом на каталог |
| Сборка внутри GUI-сессии | занимает Max художника на всё время сборки 2027 материалов |

## 3. Маппинг `ConversionPlan` → Physical Material

Имена свойств взяты из справки MAXScript, а не из памяти:

| Из плана | Physical Material |
| --- | --- |
| `base_color` | `.Base_Color` |
| текстура `BASE_COLOR` | `.base_color_map` + `.base_color_map_on = true` |
| `metallic` | `.metalness` |
| `METALLIC_GLOSS` | `.metalness_map` + `.metalness_map_on` |
| `roughness` (уже `1 − smoothness`) | `.roughness` |
| карта шероховатости | `.roughness_map` + `.roughness_map_on` |
| `NORMAL` | `.bump_map` = `Normal_Bump`, внутрь — `bitmaptexture` |
| `normal_strength` | `.bump_map_amt` — **по умолчанию 0.3**, для карт нормалей выставляем явно |
| `emission_color` | `.emission`, `.emit_color`, `.emission_map` |
| `alpha`, `alpha_cutoff` | `.Transparency`, `.cutout_map` + `.cutout_map_on` |
| `tint_color`, `tint_factor` | Color Correction поверх base color map |
| `scale` / `offset` текстуры | `bitmaptexture.coords.U_Tiling`, `.V_Tiling`, `.U_Offset`, `.V_Offset` |
| `colorspace: Non-Color` | гамма 1.0 при загрузке битмапа вместо sRGB |
| `OCCLUSION` | у Physical Material слота AO нет — умножаем в base color, как сейчас в Blender-версии |

Упаковка `_NMG` (RG нормаль, B metallic, A gloss) — единственный кусок, который
придётся **проектировать**, а не переносить: в Blender это дерево нод, в Max
нужна цепочка на Color Correction / RGB-каналах, включая восстановление синего
канала как `sqrt(1 − x² − y²)`.

## 4. Раскладка репозитория

```text
unity_pipeline_core/        ← общее ядро, единственный источник правды
unity_material_browser/     ← фронтенд Blender (выпущен, 0.12.1)
unity_material_max/         ← фронтенд 3ds Max (новый)
tools/build_extension.py    ← zip расширения Blender
tools/build_max_plugin.py   ← пакет для Max (M4)
tests/                      ← тесты ядра; свои сквозные у каждого фронтенда
```

В Blender-расширение ядро вендорится внутрь пакета — там формат требует одной
папки. У Max такого требования нет, поэтому `tools/build_max_plugin.py` кладёт
`unity_material_max` и `unity_pipeline_core` в архив рядом: импорт работает
одинаково в репозитории и после установки, вендоринг-шим не нужен.

Теги релизов различают продукты: `v*` — Blender-аддон, `max-v*` — плагин Max.
CI собирает оба пакета на каждый пуш и прикладывает к релизу только тот, чей
тег поставлен.

## 5. Этапы

**M0 — ядро внутри Max.** Прочитать существующее JSON-дерево из листенера:

```python
import sys
sys.path.insert(0, r"D:\Blender_Unity_Material_Lib")
from unity_pipeline_core import extract
print(len(extract.load_index(r"D:\UnityMaterialLib")["materials"]))
```

Печатается число материалов — фаза A работает, ещё до строчки построения.

**M1 — один материал и одна библиотека.** `ConversionPlan` → Physical Material,
`materialLibrary` → `saveTempMaterialLibrary`. Запуск сначала в листенере, потом
тем же скриптом через `3dsmaxbatch`. Проверка: `.mat` открывается в
Material/Map Browser, превью рисуется само, материал назначается на объект,
текстуры находятся по путям в `Assets/`.

**M2 — конвертация целиком.** Маппинг из раздела 3, распаковка `_NMG`, инверсия
smoothness, тайлинг, гамма. Проверка на тех же данных, что и Blender-версия:
24 материала `Bricks` и 11 `Blends`, сравнение бок о бок с Unity.

**M3 — сборка библиотеки.** Обход JSON-дерева, `.mat` на каталог, отчёт,
диффер и пересборка только изменённых — логика уже в ядре, нужен только вызов.
Проверка: полная сборка `Materials_Tiles` в фоне, повторный запуск не
перестраивает ничего.

**M4 — упаковка и UI.** Диалог PySide2/6, установка в `scripts/startup` или
`.mzp`, `tools/build_max_plugin.py`, тег `max-v0.1.0`. Сделано, см. раздел 7:
окно — четыре шага, а не одна кнопка.

Порядок неслучаен: M1 проверяет самое рискованное — что `.mat` пишется скриптом
и открывается браузером. Если это не подтвердится, меняется весь выход, и лучше
узнать об этом на одном материале, а не после написания конвертера.

## 6. Риски

| Риск | Что делаем |
| --- | --- |
| Лицензия на фоновый запуск `3dsmaxbatch` | проверяется на M1 одной командой; если фон недоступен — сборка переезжает в GUI-сессию, остальной план не меняется |
| CI без 3ds Max | ядро тестируется в CI как сейчас; Max-часть — локальным сквозным скриптом по образцу `tests/blender_material_ops.py` |
| `.tif` — 85% текстур проекта | проверить чтение штатным Bitmap на M1; если медленно, кэш конвертированных копий **вне** библиотеки (инвариант 2) |
| Ориентация зелёного канала нормали | `Normal_Bump` имеет флаги flip; сверяем на одной карте в M2 и фиксируем, а не подбираем на глаз |
| `bump_map_amt` по умолчанию 0.3 | выставляется явно из `normal_strength`, иначе рельеф тихо ослаблен на две трети |
| Расхождение Physical и Principled | цель прежняя: визуально достоверно, истина в Unity, расхождения идут в отчёт |
| Ядро обрастёт «максовыми» ветками | ядро не импортирует ни `bpy`, ни `pymxs` — правило проверяется тестом |

## 7. Что уже сделано

Поканальная упаковка (`unity_material_max` 0.3.0) — тот самый кусок из раздела
3, который надо было проектировать, а не переносить. Разбирается ровно как в
Blender-версии: нормаль из R+G с восстановлением синего как
`sqrt(1 − x² − y²)`, metallic из B, roughness как `1 − A·_GlossMapScale`, альфа
`_BCA` — в `cutout_map`, но только если канальный переключатель не объявил её
гладкостью. Считает OSL: два шейдера в `unity_material_max/osl/`, потому что
штатной картой Max корень не посчитать, а выбрать один канал без взвешивания
нечем — взвешивание тихо изменило бы metallic. Альфу OSL не требует: битмап
отдаёт её через `monoOutput`, а свиток Output масштабирует и инвертирует.
Нет OSL — нормаль идёт как есть, metallic пропускается, и то и другое пишется
в отчёт. На реальной библиотеке это 200 материалов из 384 с metallic и
roughness и 40 с cutout, которых до этого просто не было.

Окно (`unity_material_max` 0.2.0). До него единственным действием было
`Build .mat`, которое сразу открывало выбор папки: вопрос без формулировки —
непонятно, какую папку и зачем. Теперь пункт меню открывает окно с четырьмя
шагами, и каждый говорит, что ему нужно и что он нашёл.

- **Окно на PySide, а не rollout на MAXScript.** Решает не вкус: `.ms` и `.mcr`
  читаются как обычный текст и держатся в ASCII (это проверяется тестом), а
  окно должно объяснять по-русски. Python — UTF-8, и объяснение помещается.
  Импорт пробует `PySide6` (Max 2025+), потом `PySide2` (2024); версия нигде не
  предполагается, спеллинги `exec`/`exec_` и плоские/вложенные enum'ы
  разведены;
- **фаза A прямо в окне.** Max для извлечения не нужен, но человек, у которого
  открыт Max, не должен искать, чем его запустить. Библиотека, собранная
  Blender-версией, при этом понимается как есть: состояние читается с диска
  (`_ump_index.json`, `_ump_report.json`, `_ump_max_report.json`, `maxlib/*.mat`),
  а не запоминается;
- **`session.py` решает, `dialog.py` рисует** — тот же раскол, что у
  `recipe.py` и `material_builder.py`. Восемнадцать тестов
  (`tests/test_max_session.py`) идут в общей сборке без Max и без Qt;
- **прогресс и остановка** у обоих долгих шагов. Остановленная сборка не пишет
  каталог, на котором её прервали, и не переписывает отчёт: `.mat` с половиной
  каталога выглядел бы как целый;
- **выбранные пути живут вне папки плагина** —
  `%LOCALAPPDATA%\unity_material_max\settings.json`, иначе переустановка
  стирала бы ответы на все вопросы.

Написано и упаковано раньше (`unity_material_max` 0.1.1):

- `recipe.py` — вся логика фазы B без `pymxs`: слоты, гамма, тайлинг, сила
  бампа, перечень того, что не воспроизводится. Покрыт восемью тестами в
  `tests/test_max_recipe.py`, которые идут в общей сборке;
- `material_builder.py` — рецепт → Physical Material, с Normal Bump и явной
  силой бампа;
- `library_build.py` — обход JSON-дерева, `.mat` на каталог, отчёт
  `_ump_max_report.json`;
- `batch_build.py` — точка входа для `3dsmaxbatch.exe`;
- `tools/build_max_plugin.py` — два артефакта: `.zip` для ручной установки и
  **`.mzp`-автоустановщик** (перетаскивается во вьюпорт, копирует пакеты в
  `$userScripts`, макрос в `$userMacros`, подгружает его сразу);
- `tests/max_self_check.py` — проверка слоя `pymxs` внутри Max;
- CI собирает оба продукта, теги `v*` и `max-v*` разведены.

Проверено без 3ds Max: архив распаковывается в каталог скриптов, импортируется
оттуда, `library_build` грузится в отсутствие `pymxs`, а на реальном
`M_Blend_YardAsphalt_01` рецепт даёт базовую карту с гаммой 2.2, нормаль с
гаммой 1.0, тайлинг 0.5×0.5 из профиля и силу бампа 1.0 вместо максовских 0.3.

**Проверено в 3ds Max 2027.2 через `3dsmaxbatch`:** импорт ядра и плагина,
создание `PhysicalMaterial` с металличностью и шероховатостью, тайлинг на
битмапе, `Normal_Bump`, провенанс через `setAppData`/`getAppData`,
`materialLibrary` + `saveTempMaterialLibrary` (файл появляется на диске),
установка `.mzp` целиком и загрузка startup-скрипта с меню. То есть M0 и M1
закрыты на реальном Max, а не на бумаге.

**Две ловушки, найденные только запуском:**

- `plugin` — зарезервированное слово MAXScript. `local plugin = ...` в
  установщике был синтаксической ошибкой: файл не компилировался целиком,
  копирование из `mzp.run` проходило, а подтверждение и меню — нет. Установка
  выглядела как «ничего не произошло». Имена переменных в `.ms` и `.mcr` теперь
  этого избегают;
- `menuMan` в Max 2025+ **удалён**. Меню регистрируется колбэком
  `#cuiRegisterMenus`: из `callbacks.notificationParam()` берётся
  `CuiMenuManager`, дальше `mainMenuBar.CreateSubMenu` и `CreateAction` с
  таблицей макросов `647394`. Старый API молча не сработал бы;
- id у `CreateSubMenu` и `CreateAction` — **GUID-строки**, а не числа: это
  методы интерфейса, и пара чисел даёт `Type error` прямо при старте Max;
- startup-скрипты выполняются **после** того, как `#cuiRegisterMenus` уже
  отработал. Одной регистрации колбэка мало — меню появится только когда его
  кто-то перестроит. Поэтому скрипт в конце вызывает
  `maxOps.GetICuiMenuMgr()` и `LoadConfiguration (GetCurrentConfiguration())`,
  что и заставляет колбэк сработать в этой же сессии.

Остаётся непроверяемым без интерфейса ровно одно: как меню выглядит на экране.
Колбэк регистрируется, функция определена и корректно отказывается работать вне
колбэка, макрос загружается.
