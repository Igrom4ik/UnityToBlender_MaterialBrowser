# Браузер материалов Unity в Blender — проект системы

Документ описывает архитектуру подсистемы **Unity Material Browser**: генерация
Blender-библиотеки ассетов из материалов Unity, drag & drop готовых материалов на
объекты сцены и инкрементальное обновление библиотеки при изменениях в Unity.

Версия документа: черновик проекта для 1.4.0.

## 1. Задача и границы

**Что делаем.** Из каталогов Unity (`.mat` + `.meta` + текстуры) собираем
постоянную библиотеку Blender Asset Browser: материалы с корректными нодами,
текстурами, превью и каталогами, повторяющими структуру папок Unity. При
изменении материалов в Unity перестраиваем только затронутую часть библиотеки.

**Чего не делаем.** Не пытаемся получить попиксельное совпадение с рендером
Unity. Кастомные шейдеры проекта (Amplify: `Diffuse Bump Spec`, `CarBaseShader`,
блендинг по UV2/вершинным цветам) не имеют точного аналога в Cycles/EEVEE.
Цель — визуально достоверный рабочий материал, при котором **истина остаётся в
Unity**, а полный набор исходных свойств сохраняется в материале Blender для
обратной связи.

**Ключевые ограничения источника (замерено на `madout2`):**

| Параметр | Значение |
| --- | --- |
| Материалов в `Materials_Tiles` | ~2027 |
| Разных шейдеров | 15+, преимущественно кастомные |
| Формат текстур | `.tif` (~85%), `.tga`, `.png` |
| Стандартный Unity-шейдер | меньшинство материалов |
| Исходники шейдеров | доступны в проекте (`Materials_Tiles/Shaders/*.shader`), в основном сгенерированы Amplify |

Следствие: конвертация обязана быть **декларативной и расширяемой** (профили
шейдеров в JSON), а сборка — **инкрементальной и фоновой**.

### 1.1 Инварианты

Пять правил, которые не нарушаются ни одним решением ниже. Если какая-то
возможность им противоречит — от возможности отказываются, а не от правила.

1. **Unity не знает о библиотеке Blender.** Связь строго односторонняя: браузер
   только читает `Assets/`. Внутри проекта Unity не создаётся и не изменяется ни
   одного файла — ни `.json`, ни `.meta`, ни служебных маркеров. Никаких
   скриптов, хуков или `AssetPostprocessor` на стороне Unity подсистема не
   требует и не устанавливает.
2. **Библиотека хранит только пути к текстурам.** Ни один пиксель из
   `Assets/` не копируется в библиотеку. Image datablock ссылается на исходный
   файл Unity.
3. **Ничего из библиотеки не попадает в git.** Библиотека целиком — локальный
   производный артефакт: `.blend`, side-car JSON, превью, индекс. Версионируется
   только код инструмента и правила конвертации.
4. **Система локальная.** Единственный допустимый вариант размещения вне
   локального диска — облачная папка синхронизации; сетевые сервисы, БД и
   серверные компоненты не используются. Требования к облачному варианту — в 17.
5. **Читаются только явно выбранные каталоги.** Материалы, шейдеры и текстуры
   ищутся исключительно в папках, которые пользователь добавил сам
   (`sources.json`, 4.3), и в их подкаталогах. Ни `Assets/` целиком, ни проект
   Unity в целом никогда не обходятся — ни при индексировании, ни при
   разрешении GUID текстур и шейдеров (5.4). Невыбранная папка для подсистемы
   не существует: неразрешённая ссылка остаётся неразрешённой и попадает в
   отчёт, а не запускает поиск по проекту.

## 2. Как это выглядит для пользователя

0. Ставится отдельное расширение `Unity Material Browser`. Основной аддон
   `Unity Material Pipeline` для него не обязателен, но при наличии обоих список
   папок Unity у них общий (см. 4.3).
1. В разделе `Material Browser` указывается корень библиотеки Unity
   (общий список источников) и папка выходной библиотеки.
2. Кнопка `Извлечь` читает Unity и пишет JSON-дерево; кнопка `Собрать`
   запускает фоновый Blender, который делает из JSON файлы `.blend`, каталоги и
   превью. Прогресс виден в панели, отмена работает. Обычный сценарий — одна
   кнопка `Обновить библиотеку`, выполняющая обе фазы подряд.
3. Папка библиотеки один раз регистрируется в
   `Preferences > File Paths > Asset Libraries`.
4. В Asset Browser появляются каталоги `Materials_Tiles/Concrete`,
   `Materials_Tiles/Metal` и т. д. Материал перетаскивается на объект в 3D
   Viewport — назначается материал с готовым деревом нод и текстурами.
5. Параметры назначенного материала не редактируются: он связан с библиотекой, а
   истина остаётся в Unity. Кнопка `Создать редактируемую копию` запрашивает новое
   имя и делает локальный материал, который правится без ограничений (12.2).
6. Кнопка `Проверить обновления` показывает `новых N / изменённых M / удалённых
   K`. Кнопка `Собрать изменённые` перестраивает только затронутые файлы.

## 3. Структура библиотеки на диске

```text
<UnityBlenderLibrary>/            ← регистрируется как Asset Library
├─ blender_assets.cats.txt        ← каталоги (генерируются из путей Unity)
├─ _ump_index.json                ← производный индекс для быстрого диффа
├─ _ump_profiles.json             ← правила конвертации шейдеров
├─ _ump_nodegroups.blend          ← мастер-нодгруппы (UMP_UnityStandard и др.)
├─ _ump_report.json               ← последний отчёт сборки (ошибки, покрытие)
├─ .gitignore                     ← библиотека целиком вне версионирования
├─ shaders/                       ← разобранные .shader: свойства и дефолты
│  └─ Custom_Diffuse Bump Spec.json
└─ materials/                     ← зеркало структуры папок Unity
   └─ Materials_Tiles/Concrete/
      ├─ Bordur_1.json            ← распарсенный материал Unity (истина)
      ├─ Bordur_1.preview.png     ← отрендеренная иконка
      ├─ Bordur_1.blend           ← производный ассет (режим per_material)
      └─ _catalog.blend           ← производный ассет (режим per_catalog)
```

**Ключевой принцип: JSON — источник, `.blend` — производное.** Рядом с каждым
материалом лежит его распарсенное представление Unity. Любой `.blend` в
библиотеке восстанавливается из JSON-дерева **без обращения к проекту Unity**:
пересборка после правки профилей не требует ни доступа к `Assets/`, ни
закрытого Unity, ни повторного обхода 2027 файлов. Подробности слоя данных — в
разделе 3.1.

**Гранулярность `.blend` — параметр сборки, а не архитектуры.** Blender не умеет
обновить один datablock внутри `.blend`, файл всегда перезаписывается целиком,
поэтому есть два режима упаковки одного и того же JSON-дерева:

| Режим | Плюсы | Минусы |
| --- | --- | --- |
| `per_material` (по умолчанию) | обновление материала = перезапись одного файла ~150 КБ, идеальная параллельность, `.blend` лежит буквально рядом со своим JSON | ~2027 файлов, дольше первичное индексирование библиотеки Asset Browser |
| `per_catalog` | ~30 файлов, быстрое сканирование библиотеки | перезапись одного материала переписывает весь каталог целиком |

Оба режима читают один и тот же слой данных и различаются только шагом
упаковки, поэтому режим переключается настройкой и проверяется замером на
реальных 2027 материалах, а не выбирается заранее на бумаге.

### 3.1 Слой данных: JSON рядом с материалом

Конвейер разбивается на две независимые фазы:

```text
Фаза A — Extract  (чистый Python, Blender не нужен)
   Unity .mat + .meta  ──>  materials/<catalog>/<name>.json

Фаза B — Build     (фоновый Blender)
   <name>.json  ──>  <name>.blend + <name>.preview.png
```

Что это даёт:

- фаза A полностью покрывается unit-тестами без Blender и живёт в
  `unity_pipeline_core`;
- правка профилей запускает только фазу B — Unity-проект при этом может быть
  занят, недоступен или вообще отсутствовать;
- JSON — текст, поэтому дерево читаемо, диффится обычными средствами и годится
  для отладки правил; в git оно при этом не попадает (инвариант 3) — это
  локальный кэш разбора, а не исходник;
- превью лежит отдельным PNG и переживает пересборку `.blend`, не требуя
  повторного рендера.

Схема файла (`materials/Materials_Tiles/Concrete/Bordur_1.json`):

```json
{
  "schema": "ump.material/1",
  "source": {
    "guid": "…", "path": "Assets/ART/.../Bordur_1.mat",
    "hash": "sha1…", "extracted_at": "…", "extractor": "yaml|unity_editor"
  },
  "shader": {
    "guid": "113f6f…", "name": "Custom/Diffuse Bump Spec",
    "path": "Assets/.../Shaders/Diffuse Bump Spec.shader",
    "json": "shaders/Custom_Diffuse Bump Spec.json",
    "hash": "sha1…", "resolved": true, "workflow": "specular"
  },
  "material": {
    "name": "Bordur_1",
    "render_queue": -1, "lightmap_flags": 5, "double_sided_gi": false,
    "keywords": {"valid": [], "invalid": ["_EMISSION", "_NORMALMAP"]},
    "textures": {
      "_MainTex": {
        "guid": "104d16…", "path": "Assets/.../T_Bordur_BC.tif",
        "scale": [1.0, 1.0], "offset": [0.0, 0.0],
        "meta": {"srgb": true, "texture_type": "default",
                 "wrap": "repeat", "alpha_is_transparency": false}
      }
    },
    "empty_texture_slots": ["_DetailMask", "_EmissionMap", "_MetallicGlossMap"],
    "floats": {"_Specular": 0.07, "_Gloss": 0.0, "_Cutoff": 0.5},
    "colors": {"_Color": [1.0, 0.0, 0.0, 1.0], "_MulColor": [0.6, 0.6, 0.6, 0.0]},
    "ints": {}
  },
  "effective": {
    "textures": {
      "_MainTex": {"origin": "material"},
      "_BumpMap": {"origin": "material"}
    },
    "floats": {
      "_Specular": {"value": 0.07, "origin": "material"},
      "_MinZOffset": {"value": 0.1, "origin": "shader_default"}
    },
    "colors": {
      "_Color": {"value": [1.0, 0.0, 0.0, 1.0], "origin": "material"}
    },
    "stale": ["_DiffuseR", "_Normal1", "_MetallicGlossMap", "_OcclusionMap"],
    "hidden": ["_texcoord", "_texcoord2", "__dirty"]
  },
  "conversion": {
    "profile": "diffuse_bump_spec", "node_group": "UMP_UnityStandard",
    "status": "OK", "unmapped": ["_Blend_UVW2_Texture"], "warnings": [],
    "built_at": "…", "builder_version": "1.4.0"
  }
}
```

Четыре блока разделены осознанно:

| Блок | Что это | Когда переписывается |
| --- | --- | --- |
| `source` | факты о файле `.mat` | при изменении `.mat` |
| `shader` | ссылка на разобранный шейдер и его хэш | при изменении `.mat` или шейдера |
| `material` | ровно то, что записано в `.mat`, без интерпретации | при изменении `.mat` |
| `effective` | что реально применяется: материал поверх дефолтов шейдера | при изменении `.mat` **или шейдера** |
| `conversion` | результат наших правил | при правке профилей |

`effective` — тот самый «актуальный» слой: значения, которых в `.mat` нет,
подставлены из `Properties` шейдера и помечены `origin: shader_default`;
свойства, которых в шейдере нет, вынесены в `stale` и в конвертацию не идут;
служебные `[HideInInspector]` — в `hidden`. Разделение `material` и `effective`
принципиально: первый остаётся дословной записью Unity и позволяет в любой
момент пересчитать второй, когда шейдер изменится или улучшится справочник
встроенных шейдеров.

Соглашения:

- `textures` содержит **только заполненные** слоты; пустые перечислены именами в
  `empty_texture_slots` — это нужно отчёту покрытия, но не раздувает файл;
- `floats` и `colors` пишутся **целиком**, включая значения по умолчанию: именно
  они несут вид материала, когда текстур нет (см. 6.5);
- имя файла повторяет имя ассета, включая суффикс `__<guid6>` при коллизии, и
  санируется по правилам файловой системы; сопоставление всегда идёт по `guid`
  внутри файла, а не по имени файла;
- посторонние файлы в каталоге Asset Library безопасны: Blender индексирует
  только `.blend`.

**Правило стабильности имён.** При перезаписи файла библиотеки связи `Link` из рабочих
сцен сохраняются по паре «путь файла + имя datablock». Поэтому:

- имя материала = `m_Name` из Unity;
- при коллизии имён между папками добавляется детерминированный суффикс
  `__<первые 6 символов GUID>`;
- переименование материала в Unity трактуется как `MOVED` (тот же GUID) и
  логируется отдельно, потому что ломает существующие ссылки;
- локальные редактируемые копии (12.2) под правило не подпадают: их имя задаёт
  пользователь, а библиотека о них ничего не знает.

## 4. Обособление: отдельное расширение и общее ядро

Этот раздел описывает раскладку на случай, когда браузер живёт в одном
репозитории с существующим аддоном. Для отдельного репозитория — см. 16.

Браузер оформляется **отдельным расширением Blender** со своим каталогом,
манифестом, версией и ZIP. Он устанавливается и обновляется независимо от
`Unity Material Pipeline`. Общий для обеих частей код выносится в третий
каталог-ядро.

### 4.1 Структура репозитория

```text
UnityBlender_Pipline/
├─ unity_pipeline_core/               ← общее ядро, чистый Python, без bpy
│  ├─ __init__.py
│  ├─ unity_library.py                ← переезжает из аддона
│  ├─ shader_parser/                  ← универсальный разбор шейдеров
│  │  ├─ interface.py                 ← ShaderInterface, ShaderProperty, реестр
│  │  ├─ shaderlab.py                 ← .shader (ручной HLSL/CG и Amplify)
│  │  ├─ shadergraph.py               ← .shadergraph
│  │  ├─ hlsl.py                      ← кейворды и типы из .hlsl/.cginc
│  │  └─ builtin_shaders.json         ← встроенные шейдеры Unity
│  ├─ material_profile.py             ← профили шейдеров
│  ├─ material_json.py                ← схема side-car JSON, запись и чтение
│  ├─ index.py                        ← чтение и запись _ump_index.json
│  ├─ sync.py                         ← диффер NEW/CHANGED/MOVED/MISSING
│  └─ paths.py                        ← общий кэш и общий список источников
│
├─ blender_unity_material_pipeline/   ← существующее расширение (1.3.x)
│  └─ vendor/unity_pipeline_core/     ← копия ядра, кладётся сборщиком
│
├─ unity_material_browser/            ← новое расширение
│  ├─ blender_manifest.toml           ← id = "unity_material_browser"
│  ├─ __init__.py
│  ├─ registration.py / localization.py
│  ├─ preferences.py                  ← глобальные настройки (не в Scene)
│  ├─ properties.py / operators.py / ui.py
│  ├─ node_builder.py                 ← построение дерева нод
│  ├─ library_build.py                ← сборка .blend, каталоги, превью
│  ├─ preview.py                      ← рендер иконок
│  ├─ background/build_library.py     ← точка входа фонового Blender
│  ├─ resources/nodegroups.blend      ← мастер-нодгруппы
│  └─ vendor/unity_pipeline_core/     ← копия ядра, кладётся сборщиком
│
├─ unity_material_remapper/           ← Unity-плагин (без изменений)
├─ tools/                             ← сборщики обоих расширений
└─ tests/
```

### 4.2 Как ядро попадает в оба расширения

Расширения Blender не могут надёжно импортировать друг друга: путь пакета
зависит от идентификатора репозитория (`bl_ext.<repo>.<id>`), а установлены они
могут быть по-разному. Поэтому используется **вендоринг**: `tools/build_*.py`
копирует `unity_pipeline_core/` в `vendor/` каждого расширения перед упаковкой.

- Источник истины — только `unity_pipeline_core/`; каталоги `vendor/` попадают в
  `.gitignore` и создаются сборкой.
- Тест проверяет, что в собранном ZIP лежит копия, побайтово совпадающая с
  источником, — расхождение версий ядра между расширениями невозможно.
- Импорт внутри расширений: `from .vendor.unity_pipeline_core import unity_library`.
  В существующем аддоне это одна правка строки импорта в
  `operators.py` и переезд `tests/test_unity_library.py` на новый путь модуля.

Альтернатива — собрать ядро Python-wheel и объявить его в обоих манифестах через
`[build] wheels`. Механизм официальный, но добавляет риск конфликта версий wheel
между двумя расширениями, поэтому оставлен как запасной.

### 4.3 Общий кэш и общий список источников

Это ключевой момент обособления: `extension_path_user()` возвращает **разные**
каталоги для разных расширений, поэтому текущий кэш Unity-библиотеки браузеру
не виден. Ядро (`paths.py`) определяет общее место:

```python
def resolve_state_dir() -> Path:
    # 1. переменная окружения UMP_CACHE_DIR (уже поддерживается)
    # 2. bpy.utils.user_resource('DATAFILES', path="unity_pipeline", create=True)
    # 3. Path(bpy.app.tempdir) / "unity_pipeline"
```

```text
<user DATAFILES>/unity_pipeline/
├─ cache/            ← кэши индексации Unity (общие для обоих расширений)
└─ sources.json      ← список папок Unity, добавленных вручную
```

`sources.json` — общий список «мануально установленных каталогов»: папки,
которые сегодня хранятся в `scene.ump_settings.unity_libraries`. Записи имеют
тип: `materials` (папки с `.mat`) и `shaders` (папки с `.shader`, в проекте —
`Materials_Tiles/Shaders/`). Разделение нужно потому, что шейдеры обычно лежат
вне каталогов материалов, а по инварианту 5 индексируются только явно
выбранные папки: не добавленная в `sources.json` папка шейдеров означает, что
шейдеры не разрешатся, а не что их поищут где-то ещё. После переезда
папка, добавленная в аддоне пайплайна, сразу видна браузеру и наоборот.
Существующие записи в сцене мигрируют в общий файл при первом запуске; кэши из
старого каталога расширения переносятся, а при неудаче просто
переиндексируются.

Настройки самого браузера (папка выходной библиотеки, режим текстур, размер
превью) живут в `AddonPreferences`, а не в `Scene`: библиотека одна на машину,
а не на `.blend`.

### 4.4 Слои и зависимости

| Модуль | Ответственность | Импортирует `bpy` |
| --- | --- | --- |
| `core/unity_library.py` | парсинг `.mat`, `.meta`, GUID-индекс, кэш | нет |

## 5. Расширение парсера Unity

Текущий `parse_material` читает только `m_TexEnvs` и GUID. Нужно добавить:

- `m_Shader` → GUID шейдера + разрешение в имя шейдера через `.shader`/`.meta`;
- `m_Scale` / `m_Offset` для каждой текстуры (tiling → нода `Mapping`);
- `m_Floats`, `m_Colors`, `m_Ints` (`_Metallic`, `_Glossiness`, `_Cutoff`,
  `_BumpScale`, `_Mode`, `_Color`, `_EmissionColor`, …);
- `m_ValidKeywords` / `m_InvalidKeywords` (`_NORMALMAP`, `_EMISSION`,
  `_ALPHATEST_ON`) — определяют, включена ли ветка;
- `m_CustomRenderQueue`, `m_LightmapFlags`, `m_DoubleSidedGI`.

Дополнительно парсится `.meta` **текстуры** — это единственный корректный
источник цветового пространства и типа карты:

- `sRGBTexture: 1|0` → `colorspace_settings.name = "sRGB" | "Non-Color"`;
- `textureType: 1` → normal map (важно: у нормалей `sRGB` игнорируется);
- `wrapMode`, `aniso`, `alphaIsTransparency`.

Эвристика по имени файла (`_N`, `_NMG`) остаётся только запасным вариантом,
когда `.meta` не найден.

### 5.1 Универсальный парсер шейдеров

Сканирование читает не только `.mat`, но и сами шейдеры. Это снимает главное
ограничение подхода «только чтение проекта»: в `.mat` Unity сохраняет не полный
набор свойств, а шейдер знает и полный список, и значения по умолчанию, и
семантику. Файлы шейдеров лежат в тех же `Assets/`, поэтому инвариант 1 не
нарушается.

**Границы задачи.** Парсер извлекает **интерфейс** шейдера — свойства, их типы,
значения по умолчанию, атрибуты и кейворды. Он не компилирует шейдер и не
воспроизводит его логику. Без этой границы задача бесконечна: воспроизвести
поведение произвольного HLSL в нодах Blender невозможно, а интерфейс —
извлекаем и достаточен для конвертации.

### 5.2 Архитектура: единая модель и сменные бэкенды

Формат шейдера в проекте не один, поэтому парсер устроен как набор бэкендов с
общим выходом:

```text
.shader (ShaderLab: ручной HLSL/CG или сгенерированный Amplify) ─┐
.shadergraph (JSON Shader Graph, URP/HDRP)                       ├─> ShaderInterface
.hlsl / .cginc (вспомогательное обогащение)                      │
builtin_shaders.json (встроенные шейдеры Unity без исходников)   ┘
```

`ShaderInterface` — единственное, что видит остальная система:

```python
@dataclass(frozen=True)
class ShaderProperty:
    name: str            # _MainTex — имя, под которым свойство лежит в .mat
    display: str         # "Albedo (RGB)"
    type: str            # TEXTURE | COLOR | FLOAT | RANGE | VECTOR | INT
    default: object      # значение по умолчанию из шейдера
    attributes: tuple    # NORMAL, HDR, NO_SCALE_OFFSET, HIDDEN, TOGGLE, GAMMA
    range: tuple | None

@dataclass(frozen=True)
class ShaderInterface:
    schema: int
    name: str            # "Custom/Diffuse Bump Spec"
    backend: str         # shaderlab | shadergraph | builtin | material_only
    workflow: str        # metallic | specular | unlit | unknown
    properties: tuple[ShaderProperty, ...]
    keywords: tuple[str, ...]
    confidence: str      # full | partial | none
```

Бэкенды регистрируются в реестре и объявляют, какие расширения обрабатывают, —
добавление нового формата не требует правок в конвертере, профилях и сборщике.

| Бэкенд | Вход | Что даёт | Статус |
| --- | --- | --- | --- |
| `shaderlab` | `.shader` | блок `Properties`, атрибуты, `#pragma surface`; покрывает и ручные HLSL/CG-шейдеры, и сгенерированные Amplify — у них один и тот же ShaderLab-контейнер | основной, M1 |
| `shadergraph` | `.shadergraph` | свойства из JSON-графа, их reference-имена и дефолты, тип master-узла | M1, если в проекте появятся; иначе M5 |
| `hlsl` | `.hlsl`, `.cginc` по `#include` | уточнение кейвордов (`#pragma shader_feature`, `multi_compile`), подтверждение типов | обогащение, необязательный |
| `builtin` | `builtin_shaders.json` | свойства встроенных шейдеров Unity, исходников которых в проекте нет | M1 |
| `material_only` | сам `.mat` | деградация, когда шейдер не найден или формат неизвестен | всегда |

**Про Amplify отдельно.** Специальный бэкенд ему не нужен: Amplify Shader Editor
генерирует обычный `.shader`, и `Diffuse Bump Spec.shader` из проекта — ровно
такой файл с нормальным блоком `Properties`. Исходный граф (`.asset`) не
читается: он не влияет на интерфейс материала.

**Про Shader Graph.** Формат — JSON с версионированной схемой, свойства лежат
сериализованными объектами с типом (`Vector1`, `Texture2D`, `Color`, …). Здесь
есть ловушка, которой нет в ShaderLab: reference-имя свойства отличается от
отображаемого, и если автор не задал его явно, Unity генерирует имя вида
`_Texture2D_A1B2C3` — именно оно попадает в `.mat`. Сопоставление всегда идёт по
reference-имени, а отображаемое используется только в отчётах. Поскольку схема
формата менялась между версиями Unity, бэкенд проверяет версию и при незнакомой
возвращает `confidence: partial` вместо догадок.

**Деградация вместо тишины.** Если формат не распознан или разбор дал неполный
результат, `confidence` понижается, материал получает статус `PARTIAL` и
попадает в отчёт с указанием причины. Конвертация при этом продолжается по
данным `.mat` — библиотека собирается всегда.

### 5.3 Что даёт ShaderLab-бэкенд

Из ShaderLab извлекается:

| Что | Пример из `Diffuse Bump Spec.shader` | Зачем |
| --- | --- | --- |
| Полное имя шейдера | `Shader "Custom/Diffuse Bump Spec"` | матчинг профиля по имени, читаемые отчёты |
| Список свойств с типами | `_Specular("Specular", Range(0,1))`, `_MainTex(…, 2D)`, `_Color(…, Color)` | знание, какие свойства у шейдера вообще есть |
| Значения по умолчанию | `_MulColor(…) = (0.8676471,0.8676471,0.8676471,0)` | подстановка того, чего нет в `.mat` |
| Атрибуты | `[Toggle]`, `[HideInInspector]`, `[Normal]`, `[HDR]`, `[NoScaleOffset]`, `[Gamma]` | автоматическая семантика без ручных правил |
| Отображаемое имя | `_Gloss("Gloss", …)` | подсказка при написании профиля, текст в отчёте |
| Модель освещения | `#pragma surface surf StandardSpecular` | выбор workflow: specular или metallic |

**Главная находка: `.mat` содержит мусор от прежних шейдеров.** У `Bordur_1`
назначены текстуры `_MainTex`, `_BumpMap`, `_DiffuseR` и `_Normal1`, но в
`Properties` его шейдера есть только `_MainTex`, `_BumpMap` и
`_Blend_UVW2_Texture`. Значит `_DiffuseR` и `_Normal1` — остатки от материала,
который раньше был на другом шейдере: Unity их хранит, но не рендерит. Без
сверки со списком свойств шейдера конвертер подключил бы две лишние текстуры и
дал бы картинку, которой в Unity нет. Поэтому сверка обязательна, а отсеянные
свойства пишутся в JSON отдельным списком `stale`, а не выбрасываются.

**Атрибуты дают правила бесплатно:**

- `[HideInInspector]` — служебное свойство (`_texcoord`, `_texcoord2`,
  `__dirty`), в конвертацию не идёт. Ручной список `ignore` в профиле почти
  перестаёт быть нужным;
- `[Normal]` — карта нормалей независимо от имени и `.meta`;
- `[HDR]` — цвет с интенсивностью выше единицы, важен для emission;
- `[NoScaleOffset]` — tiling не применяется, ноды `Mapping` не создаются;
- `[Toggle]` / `[Toggle(_KEYWORD)]` — булев переключатель ветки, а не число.

**Workflow.** `#pragma surface surf StandardSpecular` означает specular-модель:
у `Bordur_1` вид задают `_Specular` и `_Gloss`, а не `_Metallic`. Нодгруппа
должна поддерживать оба пути — `metallic` и `specular` — и профиль выбирает
нужный, по умолчанию наследуя подсказку из `#pragma`.

### 5.4 Разрешение, справочник и кэш

**Разрешение по GUID.** GUID шейдера разрешается тем же GUID-индексом, что и
текстуры. Так как по инварианту 5 индексируются только выбранные папки, в
`sources.json` добавляется отдельный тип источника — папки с шейдерами (в
проекте это `Materials_Tiles/Shaders/`). Если шейдер не найден, материал
получает `shader.resolved: false` и обрабатывается бэкендом `material_only`.

**Встроенные шейдеры Unity** (`Standard` и подобные — в выборке проекта это
`fileID: 46` с нулевым GUID) исходников в проекте не имеют. Для них работает
бэкенд `builtin` со справочником свойств и дефолтов; сопоставление ведётся по
паре `fileID` + GUID встроенного шейдера, а конкретные значения проверяются на
реальных материалах проекта, а не берутся из памяти. Справочник заведомо неполон
и пополняется по мере встречи новых случаев; отсутствие записи — это
`confidence: none`, а не тихая подстановка.

**Кэш шейдеров.** Шейдеров десятки, материалов тысячи, поэтому каждый шейдер
разбирается один раз и кладётся в `shaders/<имя>.json` рядом с деревом
материалов — в виде `ShaderInterface`, единого для всех бэкендов. Материал
ссылается на него по GUID и хранит хэш. При изменении шейдера пересчитываются
все материалы, которые на нём сидят (категория `SHADER_CHANGED` в 9); в хэш
инвалидации входит и версия парсера, потому что улучшение бэкенда меняет
`effective` без изменения самих файлов Unity.

Модель данных расширяется без слома кэша: `CACHE_SCHEMA` поднимается до `2`,
старый кэш инвалидируется штатным путём (`load_cache` вернёт `None`).

## 6. Конвертация: профили шейдеров

### 6.1 Общая нодгруппа

Все материалы строятся вокруг одной нодгруппы `UMP_UnityStandard`:

```text
Image(BaseMap) ─┐
Image(MaskMap) ─┼─> [ UMP_UnityStandard ] ─> Material Output
Image(Normal) ──┘
```

Каждый параметр материала представлен в группе **парой**: скалярный вход со
значением из Unity и опциональный вход карты, который его перекрывает или
домножает.

| Скаляр (всегда заполнен) | Карта (подключается при наличии) |
| --- | --- |
| `Color Tint` ← `_Color` | `Base Color Map` |
| `Metallic Scalar` ← `_Metallic` | `Metallic Map` |
| `Smoothness Scalar` ← `_Glossiness` | `Smoothness Map` |
| `Normal Strength` ← `_BumpScale` | `Normal Map Color` |
| `Occlusion Strength` ← `_OcclusionStrength` | `Occlusion Map` |
| `Emission Tint` ← `_EmissionColor` | `Emission Map` |
| `Alpha` ← `_Color.a` | `Alpha` из карты |
| `Alpha Cutoff` ← `_Cutoff` | — |

Внутри группы: `Smoothness → Roughness` (`1 − x`), смешивание скаляра и карты по
правилу профиля, распаковка нормали, микс AO, сборка Emission, Principled BSDF.
При отсутствии карты работает скаляр, при наличии — правило `combine`
(см. 6.5).

Зачем: логика шейдинга живёт в одном месте. Изменение способа перевода
smoothness или AO не требует пересборки 2000 материалов — достаточно обновить
`_ump_nodegroups.blend` (при обновлении версии нодгрупп ребилд всё же
запускается, но это одна управляемая точка). Материалы остаются компактными,
файлы библиотеки — маленькими.

Для случаев, которые Principled не покрывает (двухслойный блендинг по вершинным
цветам, `_Blend_UVW2_Texture`, `_DiffuseR` + `_Normal1`), профиль указывает
альтернативную группу — `UMP_UnityBlend2` и т. п.

### 6.2 Формат профиля

Дефолтные правила лежат в самом инструменте — `unity_pipeline_core/
default_profiles.json` — и загружаются всегда; файл, указанный пользователем в
настройках, матчится первым и потому переопределяет их (16.5). Правило текстуры
поддерживает `role`, `packing`, `combine`, `channel` и `scale_from`: последнее
читает тайлинг из float-свойств шейдера, а не из слота текстуры — так устроены
слоистые шейдеры, где тайлинг лежит в `_Tile1x`/`_Tile1y`.

Первый поставляемый профиль — `amplify/layered-blend` для
`Custom/Environment/PBR_blend_materials`: он закрепляет за базовым цветом и
нормалью слой 1 (заливочный) вместо того, чтобы отдавать слот тому слою, чьё имя
файла эвристика разобрала первым, и берёт его тайлинг из `_Tile1x`/`_Tile1y`.
Слои 2–4 остаются в `unmapped` — это честный отчёт: воспроизведение блендинга по
вершинным цветам с высотой требует отдельной нодовой группы (M5).

`_ump_profiles.json` редактируется пользователем и версионируется вместе с
проектом:

```json
{
  "schema": 1,
  "profiles": [
    {
      "id": "diffuse_bump_spec",
      "match": {
        "shader_guid": ["113f6f29699ab5e4eb801bfd6ed92c1a"],
        "shader_name": ["Diffuse Bump Spec"]
      },
      "node_group": "UMP_UnityStandard",
      "textures": {
        "_MainTex":          {"input": "Base Color Map", "alpha_input": "Alpha",
                              "combine": "multiply"},
        "_BumpMap":          {"input": "Normal Map Color", "normal_packing": "rgb"},
        "_MetallicGlossMap": {"input": "Metallic Map", "channel": "R",
                              "extra": {"A": "Smoothness Map"},
                              "combine": "replace"},
        "_OcclusionMap":     {"input": "Occlusion Map", "channel": "G"},
        "_EmissionMap":      {"input": "Emission Map", "combine": "multiply"}
      },
      "floats": {
        "_Metallic":   "Metallic Scalar",
        "_Glossiness": "Smoothness Scalar",
        "_BumpScale":  "Normal Strength",
        "_Cutoff":     "Alpha Cutoff"
      },
      "colors": {
        "_Color":         "Color Tint",
        "_EmissionColor": "Emission Color"
      },
      "blend_mode": {"property": "_Mode",
                     "map": {"0": "OPAQUE", "1": "CLIP", "2": "BLEND", "3": "BLEND"}},
      "workflow": "specular",
      "ignore": ["_SpecCOlor"]
    }
  ],
  "fallback": { "id": "generic", "node_group": "UMP_UnityStandard" }
}
```

Порядок матчинга: `shader_guid` → `shader_name` (regex) → `fallback`.

Разбор шейдеров (5.1) заметно упрощает профили:

- список `ignore` почти не нужен — `_texcoord`, `_texcoord2`, `__dirty`
  отсеиваются автоматически по атрибуту `[HideInInspector]`; вручную
  перечисляются только осмысленные свойства, которые мы сознательно не
  поддерживаем;
- `workflow` по умолчанию берётся из `#pragma surface`, в профиле указывается
  только при необходимости переопределить;
- `fallback` перестаёт быть чистой эвристикой по именам: он видит тип свойства
  (`2D` / `Color` / `Range` / `Float` / `Vector`), атрибуты `[Normal]`, `[HDR]`,
  `[NoScaleOffset]` и отображаемое имя. Правило «`Range(0,1)` с именем, похожим
  на gloss/smooth, → Smoothness Scalar» работает надёжнее, чем сопоставление
  голых имён, а `[Normal]` определяет карту нормалей даже когда она названа
  `_Normal1` или `_DetailBump`.

Практический эффект: профили нужно писать не для всех 15+ шейдеров, а только
там, где `fallback` ошибается или где нужен нестандартный узел — например для
блендинга по UV2 в `Diffuse Blend 2 Textures`.

### 6.3 Отчёт покрытия

Каждая сборка пишет в `_ump_report.json` список свойств Unity, не попавших ни в
одно правило, с частотой встречаемости:

```json
{
  "shaders": [
    {"name": "Custom/Diffuse Bump Spec", "backend": "shaderlab",
     "confidence": "full", "materials": 16, "profile": "diffuse_bump_spec"},
    {"name": "unresolved:0000…f000…", "backend": "material_only",
     "confidence": "none", "materials": 14, "profile": "generic"}
  ],
  "unmapped": [
    {"property": "_Blend_UVW2_Texture", "type": "TEXTURE", "count": 61,
     "shader": "Custom/Diffuse Bump Spec"}
  ],
  "stale_dropped": [{"property": "_DiffuseR", "count": 128}]
}
```

Это рабочий инструмент: художник видит, что именно ещё не сконвертировано, и
дописывает профиль. Без такого отчёта покрытие кастомных шейдеров превращается
в угадывание. Разбивка по шейдерам показывает, куда вкладываться в первую
очередь: шейдер с 61 материалом важнее шейдера с одним, а строка
`confidence: none` означает, что сначала нужен не профиль, а поддержка формата
или запись в справочнике встроенных.

Отдельная строка `stale_dropped` — свойства, отсеянные как мусор от прежних
шейдеров. Её стоит просматривать: аномально большое число может означать не
мусор, а ошибку разбора шейдера.

### 6.4 Особые случаи

- **Упаковка нормали.** Мобильный DXT5nm хранит нормаль в `AG`. Профиль задаёт
  `normal_packing: "rgb" | "ag"`; для `ag` группа собирает `R←A`, `G←G`,
  `B = sqrt(1 − R² − G²)`.
- **Канал smoothness.** `_SmoothnessTextureChannel` = 1 означает альфу albedo,
  а не альфу mask-карты.
- **Прозрачность.** `_Mode` → `blend_method` / `Alpha Clip` + `_Cutoff`.
- **Tiling.** Ненулевые `m_Scale`/`m_Offset` добавляют одну общую ноду
  `Mapping` + `Texture Coordinate`; при разных значениях у разных карт создаётся
  отдельный `Mapping` на карту.
- **Keywords не равны выключенной ветке.** `m_InvalidKeywords` — это кейворды,
  которых нет в текущем шейдере (остались от предыдущего), а не отключённые
  функции. У `Bordur_1` там лежат `_EMISSION` и `_NORMALMAP`, при том что
  `_BumpMap` назначен и работает. Поэтому кейворды учитываются только в
  профилях стандартных шейдеров, где их семантика известна; для кастомных
  шейдеров решает факт наличия текстуры и значение параметра.

### 6.5 Материалы без текстур и смешанные случаи

Это основной случай, а не краевой: в библиотеке есть материалы с полным набором
карт, материалы вообще без текстур, где вид задан только `_Color`, `_Metallic`,
`_Glossiness`, и любые промежуточные комбинации — например, только `_MainTex` и
`_BumpMap`, а металличность и гладкость скалярные.

Правила построения:

1. **Скаляры применяются всегда.** Значения из `floats`/`colors` записываются в
   `default_value` соответствующих входов нодгруппы независимо от того, есть ли
   карты. Материал без единой текстуры даёт валидный, корректно выглядящий
   Principled BSDF: `_Color` → Base Color, `_Metallic` → Metallic,
   `1 − _Glossiness` → Roughness.
2. **Ноды текстур создаются только для заполненных слотов.** Записи
   `m_Texture: {fileID: 0}` пропускаются: пустых `Image Texture` в дереве не
   появляется. У `Bordur_1` из 14 слотов заполнено 4 — в материале будет 4 ноды,
   а не 14.
3. **Правило `combine` задаёт, что происходит при наличии карты:**
   - `multiply` — карта домножается на скаляр (поведение URP Lit для
     `_BaseMap` × `_BaseColor`, `_EmissionMap` × `_EmissionColor`);
   - `replace` — карта вытесняет скаляр (поведение Standard: при назначенном
     `_MetallicGlossMap` слайдеры `_Metallic` и `_Glossiness` игнорируются).

   Ошибка здесь заметна сразу: перемножение с `_Metallic = 0` обнулило бы
   металличность у всех материалов с mask-картой, поэтому правило задаётся
   профилем явно, а не выводится эвристикой.
4. **Отсутствие карт — не ошибка.** Статус такого материала `OK`, `texture_deps`
   пустой, предупреждения не выдаются. Статус `PARTIAL` означает только
   нерешённый GUID текстуры или непокрытое профилем свойство.
5. **Прозрачность без текстуры.** `_Color.a < 1` или `_Mode` в режиме
   прозрачности включают альфу и `blend_method` даже когда альфа-карты нет.
6. **Превью строится всегда**, в том числе для чисто параметрических
   материалов — иначе половина библиотеки выглядела бы в браузере пустыми
   плитками.

## 7. Метаданные материала

На каждом собранном материале сохраняются custom properties:

```python
material["ump_unity_guid"]   # GUID .mat — первичный ключ
material["ump_unity_path"]   # "Assets/ART/.../Bordur_1.mat"
material["ump_shader_guid"]  # GUID шейдера
material["ump_shader_name"]  # "Diffuse Bump Spec"
material["ump_profile"]      # "diffuse_bump_spec"
material["ump_source_hash"]  # sha1 содержимого .mat
material["ump_built_at"]     # ISO-время сборки
material["ump_json"]         # путь к side-car JSON относительно библиотеки
material["ump_raw"]          # блок material из JSON: все свойства Unity целиком
```

`ump_json` связывает материал с его файлом данных, а `ump_raw` (около 1–2 КБ)
дублирует блок фактов внутрь самого материала. Дублирование намеренное: после
`Append` материал уезжает в чужой `.blend`, где библиотеки может не быть, и он
всё равно остаётся самодостаточным — его можно перестроить по новым правилам и
использовать для будущего обратного экспорта в Unity.

Данные ассета: `asset_data.description` = путь Unity,
`asset_data.tags` = имя шейдера, профиль, папка, признаки (`has_normal`,
`has_alpha`, `emissive`) — это делает поиск в Asset Browser осмысленным при
2000 материалов.

## 8. Каталоги и превью

**Каталоги.** `blender_assets.cats.txt` генерируется из относительных путей
`.mat` к корню библиотеки Unity. UUID каталога — детерминированный
`uuid5(NAMESPACE_URL, "ump:" + catalog_path)`, поэтому регенерация файла не
разрывает привязки материалов к каталогам.

**Превью.** Основной путь — собственный рендер: материал назначается на
превью-объект (сфера / плоскость / куб — выбирается в настройках), EEVEE рендерит
128×128, результат пишется в `id.preview.image_pixels_float`. Это медленнее
встроенного `ed.lib_id_generate_preview()`, но полностью контролируемо и
предсказуемо работает в `--background`; встроенный оператор остаётся быстрым
режимом и проверяется на Blender 5.2 отдельно.

Превью сохраняется двумя способами сразу: внутрь `.blend` (его показывает Asset
Browser) и рядом с материалом в `<name>.preview.png`. PNG нужен, чтобы
пересборка `.blend` после правки профиля не требовала повторного рендера — если
хэш материала не изменился, готовая картинка просто загружается. Он же даёт
возможность посмотреть библиотеку любым файловым менеджером.

## 9. Индекс и диффер

`_ump_index.json` — **производный** файл: сводка полей из JSON-дерева, нужная
только для быстрого диффа. Он никогда не является единственным носителем данных
и восстанавливается обходом `materials/**/*.json`.

```json
{
  "schema": 1,
  "builder_version": "1.4.0",
  "profiles_hash": "sha1…",
  "unity_roots": ["D:/Work/madout2/Assets/ART/Environment/Materials_Tiles"],
  "materials": {
    "<mat_guid>": {
      "name": "Bordur_1",
      "json": "materials/Materials_Tiles/Concrete/Bordur_1.json",
      "blend": "materials/Materials_Tiles/Concrete/Bordur_1.blend",
      "catalog": "Materials_Tiles/Concrete",
      "unity_path": "Assets/ART/.../Bordur_1.mat",
      "source_hash": "sha1…",
      "texture_deps": {"<tex_guid>": "mtime:size"},
      "profile": "diffuse_bump_spec",
      "status": "OK"
    }
  }
}
```

Ключ инвалидации разделён по фазам:

- **фаза A** пересобирает JSON, если изменился `source_hash`, зависимость
  текстуры, хэш шейдера или версия парсера шейдеров;
- **фаза B** пересобирает `.blend`, если изменился JSON, `profiles_hash`,
  `builder_version` или версия нодгрупп.

Поэтому правка профилей не трогает JSON-дерево, а изменение `.mat` в Unity не
требует перерендера превью, если конверсия дала тот же результат.

Категории диффа:

| Категория | Условие | Действие |
| --- | --- | --- |
| `NEW` | GUID есть в Unity, нет в индексе | собрать |
| `CHANGED` | изменился `source_hash` или зависимость | пересобрать |
| `MOVED` | тот же GUID, другой путь | перенести JSON и пересобрать в новом каталоге |
| `RENAMED` | тот же GUID, другое `m_Name` | пересобрать + предупредить о ссылках |
| `SHADER_CHANGED` | изменился `.shader` или версия парсера | пересчитать `effective` и пересобрать все материалы этого шейдера |
| `MISSING` | есть в индексе, нет в Unity | пометить, **не удалять молча** |

Реализовано (0.12.0): помимо хэша `.mat` и штампов текстур диффер сверяет штамп
файла шейдера (индекс хранит `shader_path` и `shader_stamp`) и `parser_version`
индекса с версией парсера. Правка шейдера помечает его материалы как
`CHANGED` с причиной `Shader changed`, а поднятая версия парсера — все документы
сразу: улучшенный бэкенд читает те же файлы иначе. До этого обе ситуации
выглядели как «изменений нет», и исправления доходили до библиотеки только
полным повторным извлечением. `MOVED` и `RENAMED` пока сводятся к `NEW`+`MISSING`.

`MISSING` соответствует правилу проекта «ничего не удаляем автоматически»:
материал переносится в каталог `_Removed` и удаляется только явной командой.

Проверка обновлений дешёвая — она переиспользует уже существующее
кэш-индексирование Unity (`scan_library_steps`, прогресс, защита от открытого
Unity) и сравнивает хэши без сборки.

## 10. Процесс сборки

**Фаза A (Extract)** выполняется прямо в процессе Blender модальным оператором
или вообще вне Blender: она не использует `bpy`, читает `.mat`/`.meta` через уже
существующее кэш-индексирование и пишет JSON-дерево. Это быстрая операция, её
можно запускать часто.

**Фаза B (Build)** выполняется **отдельным фоновым процессом Blender**, а не в
текущей сессии:

```powershell
& $blender --background --factory-startup --python tools/build_library.py -- --job job.json
```

Причины: перезапись `.blend`, массовое создание datablock'ов и рендер превью не
должны трогать сцену пользователя, историю Undo и загруженные изображения.
Путь к исполняемому файлу берётся из `bpy.app.binary_path`.

- Прогресс передаётся строками JSON в stdout, аддон читает их и рисует
  прогресс-бар в модальном операторе (та же схема, что у существующего
  индексатора кэша).
- Отмена — завершение процесса; каждый файл пишется атомарно (`.tmp` →
  `replace`), поэтому прерывание не оставляет битую библиотеку.
- Параллелизм: до `min(cpu_count, 4)` процессов, работа делится по каталогам.
- Задание процессу — список путей к JSON-файлам, а не к `.mat`: фоновый Blender
  никогда не обращается к проекту Unity.

**Защита от конфликта.** Перед сборкой проверяется, какие файлы библиотеки
слинкованы в текущем `.blend`. Если такие есть — пользователь предупреждается, а
после сборки предлагается `wm.lib_reload`.

Оценка первичной сборки: 2027 материалов, ~0.2–0.5 с на материал с превью →
порядка 10–15 минут в 4 процесса. Последующие обновления — секунды.

## 11. Текстуры: только пути

По инварианту 2 библиотека не содержит ни одного скопированного файла текстур.
Image datablock всегда указывает на исходный файл в `Assets/`.

**Хранение пути.** В `.blend` пишется путь, относительный к файлу библиотеки
(`bpy.path.relpath`), с откатом на абсолютный, если библиотека и Unity-проект на
разных дисках. В side-car JSON параллельно хранится путь вида `Assets/...` —
независимый от машины ключ, по которому работает оператор `Перепривязать к
другому расположению проекта Unity` (массовая замена корня у всех Image
datablocks). Это же делает библиотеку пригодной для облачного сценария (17).

**Прокси-текстуры вынесены из библиотеки.** Раньше предполагалось складывать
уменьшенные копии в `proxies/` внутри библиотеки — это противоречит инварианту 2,
поэтому решение изменено: если режим просмотра всё же понадобится, производные
изображения кладутся в **локальный каталог состояния**
(`<DATAFILES>/unity_pipeline/proxies/`), который никогда не синхронизируется и не
является частью библиотеки. Сама библиотека при этом остаётся набором путей на
оригиналы. Опция по умолчанию выключена и отнесена в конец очереди (M4): сначала
нужно измерить, мешают ли 646 крупных `.tif` в реальной работе.

## 12. Односторонняя связь с Unity

По инварианту 1 подсистема ничего не устанавливает и не пишет в проект Unity.
Круг замыкается **без участия Unity в работе библиотеки** — за счёт того, что
имена совпадают:

- материал из библиотеки несёт имя Unity-материала, поэтому при экспорте FBX из
  Blender уже существующий `Igrom MaterialRemapper` находит и переиспользует
  исходный `.mat` вместо создания нового. Remapper при этом работает как
  работал: он сопоставляет имена и о существовании библиотеки не знает;
- `ump_unity_guid` в custom property материала остаётся полезным для отладки и
  ручной проверки соответствия, но требовать его чтения от Unity нельзя —
  FBX его не переносит, а дорабатывать Unity-плагин под библиотеку инвариант
  запрещает;
- существующий Scene Scan (на стороне Blender) получает признак «материал пришёл
  из Unity» и не предлагает переименовывать его по схеме `M_`, поскольку
  канонический источник имени — Unity.

**Именование — решено: дословно из Unity.** Имя datablock равно `m_Name`,
включая пробелы и нестандартные имена вроде `Bordur_3_4 1`. Схема `M_<Тело>` к
материалам из библиотеки не применяется: наличие `ump_unity_guid` — признак
исключения, который Scene Scan обязан учитывать и не предлагать переименование.
Единственное отступление — детерминированный суффикс `__<6 символов GUID>` при
коллизии имён между папками (см. 3).

### 12.1 Отвергнутые варианты и их последствия

Инвариант 1 закрывает два решения, которые технически были бы удобнее. Фиксирую
их вместе с ценой отказа, чтобы к ним не возвращались по кругу.

| Отвергнуто | Чем было бы полезно | Чем компенсируется |
| --- | --- | --- |
| Экстрактор на стороне Unity (чтение материала через Editor API) | точное имя шейдера, полный список свойств шейдера, унаследованные значения по умолчанию, реальное состояние кейвордов | **закрыто парсером шейдеров (5.1–5.4)**: имя, полный список свойств, дефолты и атрибуты читаются из самих файлов шейдеров. Остаётся непокрытым только то, что вычисляется в рантайме Unity |
| `AssetPostprocessor`, отмечающий изменённые `.mat` | мгновенный список изменений вместо обхода 2027 файлов | обход по `mtime`/размеру поверх уже существующего кэш-индексирования; проверка обновлений остаётся быстрой, потому что читает не содержимое, а метаданные файлов |

Поле `source.extractor` в схеме JSON сохраняется: оно фиксирует, что данные
получены разбором YAML, и оставляет формат открытым, если ограничение когда-то
снимут. Само поле ничего не требует от Unity.

Прежнее следствие «профиль обязан сам задавать значения по умолчанию» больше не
действует: значения, отсутствующие в `.mat`, берутся из `Properties` шейдера и
помечаются `origin: shader_default` (3.1). Профиль задаёт дефолт только там, где
шейдер не разрешён — то есть в режиме `material_only`.

### 12.2 Редактирование: правится только локальная копия

Материал библиотеки — зеркало Unity, а не рабочий материал. Правка идёт по копии
в Blender; в проект Unity подсистема не пишет ни при каких действиях
пользователя. Отсюда решается вопрос «почему параметры не редактируются».

**Способ импорта — решение аддона, а не умолчание Blender.** У библиотеки
ассетов три допустимых значения (`LINK`, `APPEND`, `PACK`), и умолчание Blender
5.2 — `PACK`, «связать и запечатать копию в текущий файл» — худшее из трёх:

| Способ | Правка перетащенного | `Ctrl+Z` после перетаскивания | Пересборка библиотеки |
| --- | --- | --- | --- |
| `Append` (умолчание аддона) | свободная, это локальная копия | откатывает полностью | через `Обновить материалы в этом файле` |
| `Link` | запрещена, поля серые | слот откатывается, но связь и материал остаются в файле | доходит до всех сцен сама |
| `PACK` (умолчание Blender) | запрещена | связь остаётся в файле | не доходит вообще |

Замерено на Blender 5.2: undo не выгружает библиотечные данные — после отката с
`Link` в файле остаются и материал, и запись `bpy.data.libraries`. Поэтому по
умолчанию аддон выставляет `Append`: перетаскивание ведёт себя как обычное
действие Blender, а обновление из библиотеки остаётся явной кнопкой. `Link`
доступен настройкой для тех, кому важнее автоматическое распространение
пересборки. Оператор регистрации выставляет выбранное значение и чинит уже
добавленную запись, а переключение настройки применяется к ней сразу.

Инвариант 1 при этом не зависит от выбора: в Unity не пишется ничего ни в одном
режиме. Что режим `Append` действительно меняет — правка перестаёт требовать
отдельного шага, поэтому правило «правим только копию с новым именем» держится
уже не запретом, а именем: пока имя совпадает с Unity-материалом, экспорт FBX
переиспользует исходный `.mat` и правки просто теряются. Оператор
`Создать редактируемую копию` остаётся тем, что делает расхождение осознанным.

Раздел 7 при этом остаётся в силе: `ump_raw` нужен именно потому, что материал
может уехать в чужой `.blend` через копию, описанную ниже.

**Оператор `Создать редактируемую копию`** (реализован в 0.10.0). Вызывается из
пай-меню `Ctrl+Shift+M` в 3D-виде, из меню-шестерёнки вкладки материала и из
панели аддона:

1. диалог просит новое имя, предзаполняя `<имя Unity>_edit`; совпадение с именем
   библиотечного материала и любое занятое имя отклоняются **до** применения;
2. связанный материал становится локальным и копируется в текущий `.blend` со
   всеми нодами; пути текстур сохраняются как есть — они и так ведут в `Assets/`
   (инвариант 2), копирование пикселей не происходит;
3. копия назначается в слоты выделенных объектов вместо библиотечного материала;
4. библиотека не перезаписывается, файлы Unity не открываются на запись.

Дальше это обычный материал Blender: параметры, ноды, текстуры и шейдер правятся
без ограничений.

**Метаданные копии.** `ump_unity_guid` с копии **снимается** — она больше не
представляет материал Unity, и ни диффер (9), ни Scene Scan не должны считать её
зеркалом. Вместо него пишется происхождение:

```python
material["ump_derived_from"]  # GUID исходного материала Unity
material["ump_derived_name"]  # имя библиотечного материала на момент копирования
material["ump_derived_hash"]  # его ump_source_hash на момент копирования
```

Следствие для Scene Scan: копия — материал, созданный в Blender, поэтому
исключение из 12 («не переименовывать по схеме `M_`») на неё не распространяется
и обычные правила именования снова применяются. Имя пользователь задал сам, так
что это не сюрприз, а ожидаемое поведение.

**Что происходит в Unity.** `Igrom MaterialRemapper` сопоставляет материалы по
имени, поэтому копия с новым именем при экспорте FBX даёт **новый** `.mat`, а
исходный материал Unity остаётся нетронутым. Это и есть техническая гарантия
правила «правим только копию»: совпадение имён — единственный путь, которым
правка могла бы дойти до Unity, и новое имя его закрывает. Отсюда же запрет
называть копию именем оригинала.

**Обновление библиотеки копию не трогает.** Копия локальна, в индексе её нет,
категории диффа к ней не применяются. Расхождение показывается по запросу:
`ump_derived_hash` сравнивается с текущим `source_hash` исходного материала, и
оператор сообщает «исходный материал Unity изменился после копирования».
Автоматического слияния нет — обратный перенос правок относится к M6.

| Что нужно сделать | Действие | Где остаётся истина |
| --- | --- | --- |
| Использовать материал как в Unity | drag & drop из Asset Browser | Unity |
| Изменить материал только для Blender | `Создать редактируемую копию` | локальный `.blend` |
| Изменить материал в проекте | правка в Unity + `Собрать изменённые` | Unity |

## 15. Сборка, версии и CI

- `tools/build_extension.py` получает параметр «какое расширение собирать»:
  каталог источника и манифест перестают быть константами модуля. Перед
  упаковкой сборщик копирует `unity_pipeline_core/` в `vendor/` выбранного
  расширения, после упаковки — проверяет наличие копии в ZIP.
- `tools/build_release.py` кладёт в комплект три архива: пайплайн, браузер и
  Unity-плагин.
- **Версии независимые.** `unity_material_pipeline` продолжает линию `1.3.x`,
  `unity_material_browser` стартует с `0.1.0`. Версия комплекта равна версии
  пайплайна как ведущей части; тег `vX.Y.Z` по-прежнему сверяется с манифестом
  пайплайна, а версия браузера проверяется отдельной сверкой манифеста и
  `CHANGELOG`.
- В workflow добавляются пути `unity_material_browser/**` и
  `unity_pipeline_core/**` в фильтры `push`/`pull_request`, а в шаг валидации —
  второй вызов `blender --command extension validate`.
- Правило проекта «версия правится и в манифесте, и в `__init__.py`»
  распространяется на второе расширение.

## 16. Перенос в отдельный проект

Реализация ведётся в **новом репозитории**. Раздел 4 описывает раскладку на
случай, когда оба расширения живут в одном репозитории; при отдельном проекте
она упрощается.

### 16.1 Раскладка нового репозитория

Проект размещается в `D:\Blender_Unity_Material_Lib`.

```text
D:\Blender_Unity_Material_Lib\    ← новый репозиторий (только код инструмента)
├─ unity_pipeline_core/           ← ядро: парсер, схема JSON, профили, диффер
├─ unity_material_browser/        ← расширение Blender
│  └─ vendor/unity_pipeline_core/ ← копия ядра, кладётся сборкой
├─ tools/build_extension.py
├─ tests/
├─ docs/MATERIAL_BROWSER_RU.md    ← этот документ

```

Ядро переезжает в новый проект и становится его частью. Вендоринг из 4.2
остаётся нужен только внутри нового репозитория (ядро → расширение); механика
двух расширений в одном репо из 4.1 не применяется.

**Три места, которые нельзя путать:**

| Что | Где | Версионируется | Синхронизируется |
| --- | --- | --- | --- |
| Код инструмента | `D:\Blender_Unity_Material_Lib\` | да, git | нет |
| Библиотека ассетов | отдельный каталог, например `D:\UnityMaterialLibrary\` или папка облачного диска | нет | да, если выбран облачный сценарий |

каталогом разработки. Если всё же удобнее держать рядом — только в подкаталоге,
занесённом в `.gitignore` целиком.

Проект Unity (`D:\Work\madout2`) остаётся отдельным и доступным только на
чтение — инвариант 1.

### 16.3 Связь двух проектов

Проекты остаются независимыми и связаны только форматами:

- общий каталог состояния и `sources.json` (4.3) — список папок Unity виден
  обоим;
- side-car JSON (3.1) — общий формат данных о материале;
- имена материалов Unity — основа remap в `Igrom MaterialRemapper`.

Синхронизация кода между проектами не предполагается: если парсер в новом
проекте уйдёт вперёд, старый аддон продолжит работать на своей копии, потому что
формат кэша версионирован (`CACHE_SCHEMA`), а несовместимый кэш просто
переиндексируется.

### 16.4 С чего начинать

1. Создать репозиторий и перенести пункты 16.2.
2. Реализовать фазу A целиком (M1): парсер `.mat` → JSON-дерево, с тестами на
   трёх типах материалов — полный набор карт, только скаляры, смешанный.
3. Добавить парсер шейдеров и слой `effective` (M1b). Порядок именно такой:
   без него отчёт покрытия считает мусорные свойства вроде `_DiffuseR`
   настоящими и уводит проектирование профилей не туда.
4. Прогнать фазу A на всех 2027 материалах и посмотреть отчёт: сколько шейдеров
   разобралось с `confidence: full`, какие свойства остались `unmapped`, сколько
   материалов ушло в `material_only`. **Только после этого** проектировать
   конкретные профили.
5. Дальше M2 и M3 по разделу 13.

Такой порядок даёт полезный промежуточный результат без Blender: JSON-дерево
само по себе — уже пригодный к использованию срез библиотеки материалов Unity.

### 16.5 Что версионируется

В git нового проекта идёт только инструмент:

```gitignore
# библиотека — локальный производный артефакт
/library/
*.blend
*.blend1
_ump_index.json
_ump_report.json
vendor/
```

- **в git:** код ядра и расширения, `tools/`, `tests/`, документация,
  **дефолтные профили шейдеров** (`profiles/*.json` — это правила конвертации,
  часть инструмента);
- **не в git:** сама библиотека целиком, side-car JSON, превью, индекс, отчёты,
  каталог состояния, вендоренные копии ядра.

Профили существуют в двух местах: дефолтные в репозитории инструмента и
локальная копия `_ump_profiles.json` в библиотеке, которая переопределяет
дефолтные. Первая версионируется, вторая — нет.

## 17. Локальное размещение и облачная папка

Система локальная: никаких серверов, БД и сетевых сервисов. Допустимый вариант
совместной работы — библиотека в папке облачной синхронизации (OneDrive,
Dropbox, Google Drive). Из этого следуют четыре требования.

**1. Пути к текстурам должны переживать смену машины.** У второго художника
проект Unity лежит по другому пути, и относительные пути из `.blend` указывают
в пустоту. Механизм: машинно-независимый ключ `Assets/...` в side-car JSON плюс
локальная настройка «корень проекта Unity» в `AddonPreferences`. Оператор
`Перепривязать` пересобирает пути у всех Image datablocks под текущую машину.
Проверка расхождения запускается при открытии раздела браузера, а не молча.

**2. Собирает одна машина за раз.** Параллельная сборка с двух машин в одну
облачную папку даёт конфликтные копии файлов. Защита — lock-файл
`_ump_build.lock` с именем машины и временем: перед сборкой он проверяется, при
чужом активном локе сборка не начинается и выводится, кто её держит. Это
кооперативная блокировка, а не гарантия, — от неё требуется предотвращать
случайность, а не злой умысел.

**3. Индекс восстановим.** `_ump_index.json` — самая вероятная точка конфликта
синхронизации, поэтому он производный (9): при повреждении или конфликтной копии
он пересобирается обходом `materials/**/*.json` без обращения к Unity.

**4. Режим упаковки выбирается под облако.** Облачные клиенты плохо переносят
частую перезапись тысяч мелких файлов. Если библиотека лежит в синхронизируемой
папке, `per_catalog` предпочтительнее: обновление трогает десятки файлов вместо
тысяч. Для чисто локальной работы выгоднее `per_material`. Это дополнительный
аргумент к тому, что режим упаковки остаётся настройкой (3).

Локальный каталог состояния (`<DATAFILES>/unity_pipeline/`: кэши индексации,
`sources.json`, прокси) **никогда не размещается в облаке** — он привязан к
машине и её путям.

### 18.1 Отступления от проекта и их причины

| Проект | Реализация | Причина |
| --- | --- | --- |
| Общая нодгруппа `UMP_UnityStandard` | дерево строится напрямую: `Image → Principled` со вспомогательными узлами | материал читается и правится художником прямо в редакторе нод, без вскрытия группы; цена — изменение логики требует пересборки библиотеки, что диффер и так отслеживает |
| Фаза B в отдельном фоновом процессе Blender | модальный оператор в текущей сессии; материалы создаются, пишутся и сразу удаляются | одна движущаяся часть вместо трёх (процесс, протокол, отмена); сессия пользователя не засоряется, Esc работает. Фоновый процесс остаётся вариантом, когда время сборки станет проблемой |
| Ядро в `vendor/unity_pipeline_core/` | ядро вендорится в `unity_material_browser/core/` | короче путь импорта; сборщик копирует и сверяет копию побайтово |
| `wm.previews_ensure()` как быстрый режим | собственный рендер в изолированной сцене | встроенная генерация асинхронна и в фоне не рендерит вовсе; свой рендер работает одинаково в GUI и `--background` |
| Прокси-текстуры (M4) | не реализованы | по инварианту 2 библиотека остаётся набором путей; включать только по факту замера |

**Индексирование всего проекта убрано в 0.9.0.** До 0.8.0 существовал третий тип
источника — «Весь проект Unity» — и оператор, который поднимался от папок
материалов вверх до `Assets/` и индексировал все `.meta` (~90k файлов, ~20 с).
Он появился в реализации, в проекте описан не был и прямо противоречит
инварианту 5, поэтому удалён вместе с кэшем этого индекса. GUID теперь
разрешаются только по выбранным папкам материалов и текстур/шейдеров;
ненайденная текстура остаётся `resolved: false` и попадает в отчёт, а панель
предлагает добавить её папку, а не проект. Записи прежнего типа в настройках
отбрасываются при первом запуске: молчаливое превращение их в папку материалов
означало бы тот же обход всего проекта под другим именем.

### 18.2 Добавлено сверх проекта

- **Доверие к цветовому оттенку.** `_Color` не умножается на базовую текстуру,
  если шейдер кастомный и намерение не подтверждено атрибутом `[MainColor]` или
  профилем. На `Concrete` это 326 материалов, которые иначе были бы перекрашены.
- **Заголовок `[Header(Albedo)]` — тоже доказательство** (0.10.0). Amplify не
  пишет `[MainColor]`, но кладёт цвет под заголовок альбедо рядом с картой
  альбедо: `[Header(Albedo)][Space]_Color("Color", Color)` в
  `Custom/PBR_Packed_Alpha`. Это то же утверждение другими словами, поэтому
  парсер сохраняет заголовок свойства, а правило доверия принимает его наравне
  с атрибутом. Без этого материалы вроде `M_Bricks_09_Yellow_01` собирались
  серыми при живом `_Color` в Unity. Заодно доказательство переехало в сам
  документ (поля `main_color` и `group` у цвета в `effective`): фаза B работает
  по JSON и интерфейса шейдера не видит, так что раньше `[MainColor]` на этом
  шаге не учитывался вовсе.
- **Приоритет ролей текстур.** Роль назначается по уверенности: атрибут →
  точное имя → эвристика. Без этого `_DetailAlbedoMap` забирал слот базового
  цвета у `_MainTex` просто потому, что сортируется раньше.
- **Detail- и secondary-карты** сознательно не подключаются и попадают в отчёт.
- **Счёт ненайденных текстур — только по используемым слотам** (0.12.0). Раньше
  «с ненайденными текстурами» включало слоты от прежних шейдеров, которые тот же
  отчёт тут же перечислял в `stale_dropped`: на папке `Blends` это 11 материалов
  из 11 вместо 4, а в собранной библиотеке — 63 из 384. Unity такой слот тоже не
  рендерит, поэтому в счётчик попадают только текстуры, дожившие до `effective`.

### 18.3 Что показывает отчёт на реальных данных

`Concrete`, 514 материалов: 13 из 14 шейдеров разобраны с `confidence: full`,
сборка без ошибок. В `unmapped` остаются `_BlendMask`, `_DiffuseR`, `_DiffuseG`,
`_NormalB` — многослойные блендинг-шейдеры, которым один Principled не
эквивалентен. Это и есть список кандидатов на первые профили с отдельными
нодовыми группами.
